## Judgment calls worth a reviewer's eyes

1. **AC2's idea-honesty rule, broadened beyond the plan's literal shorthand.** The plan

   AC2's own wording ("typing an idea without ticking recreate shows...") does not condition
   on `repo`. Implemented as `!recreate` (regardless of `repo`) always produces an idea-field
   message — the T-9 line if idea is typed, else "say what you want to build, or tick
   recreate" — reasoned in `src/start/request.ts`'s `validateIdea` comment: v1's
   `BuildPlan.mode` is always `'recreate'`, so unticking recreate is a dead end regardless of
   what else is filled in.
2. **AC4's resume test is simulated, not a literal process kill.** Tested two ways instead:
   (a) the marker is proven durably written to disk at each phase, re-read independently
   inside the test, not from in-memory state; (b) a marker is hand-written to simulate a
   crash and `resumeIfMarked` is called directly (the same function activation would call
   after a real reload) with a stubbed confirm. A literal kill of a nested vscode-test
   subprocess was judged not worth the added fragility over (a)+(b).
3. **`test/unit/start-view.test.ts` caught a real bug while being written**: the first draft
   ran `view.ts`'s exported `startScript()` in isolation, which has no `post()`/`save()`
   (those come from `page.ts`'s bootstrap, prepended only inside `renderPage`) — three tests
   threw `ReferenceError`s. Fixed by extracting the script from `renderStartHtml`'s actual
   combined output instead, which is what a real webview receives.
4. **`build.ts` has no `vscode` import at all**, extending the `core.ts`/`doctor.ts` house
   style. Every VS Code effect (progress, cancellation, the Resume/Discard prompt,
   `globalStorageUri`, `workspaceState`) is a plain injected parameter, wired by
   `extension.ts`/`panel.ts`. This means the write-ahead marker, language refusal, and
   end-to-end fixture build (AC3-AC5) all run under plain `mocha` with the REAL repo-tour
   core, not vscode-test — a larger design decision than the locate file explicitly called

5. **A build-time refusal was initially ONLY a notification toast — a real gap, fixed.**
   Re-reading the DoD's "the Go-only fixture is refused with the reason in the form" after

## Finding 1 — `resumeOnActivate` never cleared its own bookmark (`0306aa0`)

**The defect.** `src/extension.ts` set `workspaceState`'s `buildTutorials.currentBuild` at the
start of every build and nothing ever cleared it, and `resumeOnActivate` committed to
`loadCore(…)` **and** a `withProgress` notification before asking whether there was anything to
resume — it only found that out inside `resumeIfMarked`, after both costs were already paid. So
after the first build ever run in a workspace (success, refusal, or cancel — all left the key
set), every future activation of that window reloaded the whole repo-tour core and flashed an
empty progress notification, forever.

**The fix.** The cheap question first. `readFreshMarker(target, now?)` is new in
`src/start/build.ts` — one `fs.readFileSync` and a clock comparison, applying the same 6-hour
rule `resumeIfMarked` already had (now factored so both share one rule, one place). If there is
no marker, or it is older than 6 hours, `resumeOnActivate` clears the key and returns **before
any core load and before any UI**. Only a fresh marker pays for the core and the Resume/Discard
offer.

The key is now documented as what it actually is: a pointer at a possible marker, nothing more.
The durable state is `plan.json` on disk, which is what T-4 detects — never this key. So
`forgetUnlessResumable` clears it whenever no marker is left at the target: after a successful
build, a refusal, a cancel, or a Discard. A dismissed prompt or a failed resume leaves the
marker, and so keeps the key, for next time. A fresh marker with a MISSING core is the one case
the key survives on purpose: the marker is still good, it is the core that is absent, and
`buildTutorials.doctor` is where that gets explained.

**The test seam.** `resumeOnActivate` is exported and takes `deps: ResumeDeps` — `loadCore`,
`withProgress`, `confirm` — defaulted to the real ones, injected exactly the way
`src/start/build.ts` already injects `git`. That is the only way to make "it loaded nothing and
opened nothing" an assertion rather than a claim: neither is observable from outside otherwise.
(`ResumeDeps`'s members are declared as function-valued properties, not method shorthand,
because `confirm` is handed to `resumeIfMarked` unbound and `@typescript-eslint/unbound-method`
rightly refuses that for a method.)

**The test** — `test/extension.test.ts`, vscode-test, 5 new cases. It has to be a vscode-test:
`workspaceState` is not fake-able and not constructible outside an extension host.
`Extension.activate()` is idempotent within one process, so staging a genuine second activation
is not possible; calling the exported function with the same real `ExtensionContext` is as close
as the platform allows, and is exactly the code path activation runs.

- a remembered target with **no marker** → 0 core loads, 0 notifications, 0 prompts, key cleared
- a marker **7 hours old** → same, and the stale marker is left on disk (only the key goes)
- **no remembered target** → nothing happens, nothing loads
- a **fresh marker** → the offer DOES appear, core loaded once, progress opened once, message
  text asserted; dismissing leaves marker and key (this is the discriminator — without it the
  three cases above would pass against a function that did nothing at all)
- **Discard** → marker removed AND key cleared

## Finding 2 — `plan.json`/`request.json` were not written atomically (`e00eae6`)

**The defect.** `writeMarker` used temp-file + rename two functions away, with a comment saying
why; the actual deliverable was two plain `fs.writeFileSync` calls. A crash mid-write could
leave a truncated, invalid-JSON `plan.json`, and a Discard (or a marker gone stale) would leave
it there with nothing to signal it was broken, for T-4's walk to trip over.

**The fix.** `writeJsonAtomic(filePath, value, ops?)` factors out the marker's own pattern —
serialise to `<file>.tmp` in the same directory, then rename over the real name — and all three
writes now go through it. The order is deliberate: `request.json`, then `plan.json`, then the
marker is deleted. At every instant on disk there is either a marker (so a Resume finishes the
job) or a complete plan; never a half file with nothing pointing at it. `FsWriteOps`
(mkdir/write/rename) is injectable through `BuildContext.writeOps`, the same house style as
`git`, because staging a crash at the exact instant that matters is not possible otherwise.

**The tests** — `test/unit/build.test.ts`, 4 new cases:

- `writeJsonAtomic` with a `renameSync` that throws → **no file at the destination at all**,
  and the complete content sitting in `<file>.tmp`. This is the assertion that dies if the fix
  is reverted: a plain `writeFileSync` leaves the destination behind.
- the same write uninterrupted → lands complete, temp file gone (discriminates)
- a crash renaming onto `plan.json` during a real end-to-end build → `outcome.ok` false with
  that reason, **no `plan.json`**, and a marker still there at phase `write`, still fresh enough
  that activation would offer to resume it
- rename order recorded through the seam → deliverables are exactly
  `['request.json', 'plan.json']`, the marker was renamed into place ≥4 times (once per phase,
  proving it uses the same helper), and it is removed only once both deliverables are complete

## Finding 3 — inbound webview messages were unvalidated (`707d935`)

**The defect.** `webview.onDidReceiveMessage((message: InboundMessage) => …)` was a compile-time
promise about a value arriving from outside the compiler's reach. The reviewer fed the real
compiled `handleStartMessage` three probes and all three threw: a non-string `repo`
(`TypeError: repo.trim is not a function`), a null payload (`Cannot read properties of null`),
an unknown `type` (the exhaustive `default` branch). Through the real listener — `void
this.onMessage(message)` — each became an unhandled promise rejection.

**The fix.** `parseInboundMessage(raw: unknown): InboundMessage | null` in
`src/start/protocol.ts` is now the only way in. `type` must be one of the five known strings,
and the payload must be exactly the shape that type promises: `idea`/`repo`/`target` strings,
`recreate` a boolean, `dial` one of `DIALS` (read from `request.ts`, so a fourth dial position
needs no edit here), `skin` a string. It returns a **fresh** object carrying only the known
fields, so nothing extra reaches `validateRequest`, the panel's state, or `request.json`. It
never throws — a caller that cannot trust its input cannot be asked to catch, either.

`StartPanel.onMessage` parses first and ignores a `null`: no reply, no state change, no throw.
It says so once per panel through the new optional `StartPanelDeps.log`, which
`src/extension.ts` wires to the existing "Build Tutorials" output channel — enough to explain a
page that has quietly stopped working, without letting a looping or malicious page fill the log.
`handleStartMessage` keeps its typed signature and its exhaustive `default` branch, which is now
genuinely unreachable rather than a runtime guard. `dispatchForTest` takes `unknown`, like the
real listener, so a test can feed it exactly what a real webview could.

**The tests** — 11 unit (`test/unit/protocol.test.ts`) + 2 vscode-test (`test/start.test.ts`):

- the reviewer's three probes **verbatim** → `null` each; plus `null`/`undefined`/a number/a
  string/an array/`{}`/`{type: 7}`
- each request field with the right name and the wrong type, one at a time (including
  `recreate: 'true'` and `dial: 'turbo'`), and `dial` missing entirely → `null`
- positives so the guard is not trivially "always null": both form messages round-trip
  unchanged, all three dial positions, `pick:repo`/`pick:target` with and without the empty
  payload the real client actually sends, `skin:set` with and without a string skin, and a
  parsed message really being accepted by `handleStartMessage`
- unknown extra keys are dropped rather than carried into the request
- through the panel: six probes, each resolving `undefined` with no throw, panel state
  untouched, and **exactly one** log line for the six (the "logs once" rule, literally); a
  well-formed message through the same path as the discriminator
