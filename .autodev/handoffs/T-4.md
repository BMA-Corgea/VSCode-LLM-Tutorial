## What's in `src/walk/model.ts`, `store.ts`, `step-protocol.ts` (the part that's real)

Read the files themselves for the full doc comments; this is the shape, for a fast resume:

- **`model.ts`** (no `vscode`): `Progress { schemaVersion: 1; current: string | null; steps:
  Record<string, { status: 'pending'|'done'; dial?: Dial; transcript?: unknown[] }> }` — `Dial`
  is IMPORTED from `../start/request.js` (type-only-safe reuse, not a duplicate union — reading
  from `src/start/**` is fine, only EDITING it is DO-NOT-TOUCH). Plan-shaped types
  (`PlanLike`/`StepLike`/`ChapterLike`/`OptionLike`) are a hand-rolled duck-typed mirror of
  repo-tour's real `BuildPlan`/`Step` (repo-tour `src/build/types.ts`), matching
  `src/start/build.ts`'s own `BuildPlanLike` precedent — **deliberately NOT** a `import type`
  from `repo-tour/build`/`repo-tour/types`, even though repo-tour's `package.json` now DOES
  ship a real `exports` map (T-11 has apparently landed since `src/core.ts`'s header was
  written — confirmed by reading repo-tour's `package.json` directly) which would make a
  type-only import resolve fine today. Duck-typing was chosen anyway for consistency with the
  established house style and so this file needs no edit if repo-tour's real types grow a
  field this walk never reads. Functions: `emptyProgress(plan)`, `currentStep`, `nextStepId`/
  `prevStepId` (both `null` at the ends, both sort a COPY by `ordinal` defensively rather than
  trusting array order), `setCurrent`, `markDone`, `setDial`, `treeModel(plan, progress)` →
  `TreeChapterNode[]` (a chapter with zero steps is filtered out), `statusText(plan, progress)`
  → the literal `"step N / M · <dial>"` AC6 wants, falling back to `'manual'`
  (`FALLBACK_DIAL`) when the current step has no per-step dial override recorded — **a
  judgment call**: T-4 never reads the START SCREEN's global dial (`request.json`'s
  `dial` field) at all, only per-step overrides in `progress.json`; "manual" can never
  overstate what has happened to a step that has no override yet. T-5 may want to thread the
  real global default through instead — flagged here, not fixed, since it's out of this
  ticket's scope.
- **`store.ts`** (no `vscode`): `hasPlan(target)`, `loadPlan(target)` (throws if unreadable —
  callers check `hasPlan` first), `loadProgress(target, plan)` (missing/corrupt →
  `emptyProgress(plan)`, never a throw), `saveProgress(target, progress)`. **Reuses
  `buildDir`/`writeJsonAtomic` from `../start/build.js`** rather than reimplementing the

## Design decisions for the NOT-STARTED steps — read this before writing step 2/4/5/6

These are conclusions from this session's own analysis (spec + locate + plan + T-3's code +
the real sql-gauntlet plan.json + repo-tour's schema, all read in full before any code was
written). They are judgment calls, not commands — but re-deriving them from scratch would
waste real time, so they're recorded here.

1. **`WalkSession` (step 5) must have ZERO `vscode` import, value OR type**, exactly like
   `src/skins.ts`'s `SkinStore`. Reason, confirmed by reading `esbuild.mjs`: the
   `test/unit/*.test.ts` bundle's esbuild config marks `external: ['repo-tour', 'mocha']` —
   **not `vscode`** — so anything reachable from a `test/unit/` file that touches the real
   `vscode` module as a VALUE (not erased by `import type`) will fail to bundle at all
   (`Could not resolve "vscode"`). Since the plan's own step 5 explicitly asks for "unit test
   of the state machine with fake adapters," `session.ts` needs a **duck-typed** `WalkAdapters`
   interface (own methods: `setTree`, `setPanel`, `setStatus`, `revealEditor`, `clearEditor`,
   `openFile`, `fileExists`, `loadPlan`, `loadProgress`, `saveProgress` — plain functions, no
   `vscode.ExtensionContext` type anywhere in this file) that `src/extension.ts` wires to the
   REAL `tree.ts`/`step-panel.ts`/`editor.ts`/`status.ts` (which DO import `vscode` for real,
   and are therefore only ever exercised via `test/walk.test.ts`, the vscode-test file, never
   under plain mocha).
2. **Where `note` and `skin` live**: NOT in `WalkSession`/`Progress` — they are the STEP
   PANEL's own small local state, exactly mirroring `StartPanel`'s `problems`/`skin` in T-3.
   `StepViewProvider` (step 4) holds `private note: string | undefined` and `private skin:
   string` (read once from `globalState` via `readSkin`, same key pattern as T-3), and builds
   the `StepViewState` passed to `handleStepMessage`/`renderStepHtml` by COMBINING its own
   `note`/`skin` with whatever `WalkSession` last pushed (`plan`, `progress`, `step`,
   `fileExists`) via `WalkAdapters.setPanel(view)`. `note` is cleared whenever the pushed
   view's `step.id` differs from the previously pushed one (real navigation) but SURVIVES a
   same-step refresh (e.g. a `dial:set` on the step you're already looking at, which still
   calls `setPanel` so the status bar's "· <dial>" updates) — implement this as: `if
   (this.lastView?.step.id !== view.step.id) this.note = undefined;` before storing the new
   view and re-rendering.
3. **`WalkSession.refresh()` should take a `revealEditor: boolean` parameter.** Real
   navigation (`open`, `goTo`) reveals+decorates; `setDial`/`markDone` on the CURRENT step
   should refresh the tree/panel/status but skip re-revealing the editor (calling
   `showTextDocument`/`revealRange` again on every dial click would jump/re-center the editor
   for no reason — not incorrect, just needlessly janky). `goTo` is the only place that also
   needs to `saveProgress` AFTER updating `current`; `setDial`/`markDone` persist too, just
   without the reveal.
4. **`goTo(stepId)` must silently ignore an unknown id** (`!plan.steps.some(s => s.id ===
   stepId)` → return, no-op) rather than throwing — a stale tree item or a hand-typed command
   argument should never crash the session.
5. **Decorations have no read-back API.** `vscode.TextEditor.setDecorations(type, ranges)` is
   write-only — there is no `getDecorations()` anywhere in the VS Code API. `editor.ts`'s
   decorator (name it `StepDecorator`, a small class, not module-level mutable state) MUST
   expose an explicit test seam — e.g. `getLastRangeCountForTest(): number` — because plan step
   7's own verification line ("decorations applied (count via the session's test seam)")
   is literally impossible any other way. Track `private lastEditor: vscode.TextEditor |
   undefined` so `clear()` can un-decorate the RIGHT editor (not just whatever
   `window.activeTextEditor` happens to be, which may have changed by the time `clear()` is
   called), and dispose the `TextEditorDecorationType` itself in `WalkSession.dispose()`.
6. **The file-exists check gates BOTH the "Open the file" button's enabled state AND whether
   the editor auto-reveals at all.** In manual-dial mode with nothing written yet (T-5's job),
   `<target>/<step.target.file>` genuinely does not exist — `vscode.workspace.openTextDocument`
   on a missing path REJECTS, so `WalkSession.refresh()` must check
   `adapters.fileExists(absPath)` BEFORE calling `revealEditor`, and call `clearEditor()`
   instead when it's false. This means **`test/walk.test.ts`'s fixture must pre-populate the
   target directory with real files** at the paths the hand-written plan's steps point to
   (plan step 7's own wording — "write files + a hand-written plan" — says this literally);
   the fixture is simulating "a target folder that already has some content," not exercising
   T-5's dial logic at all, which is explicitly out of scope here.
7. **The webview-view reveal risk (plan's named risk, step 4/7).** Not yet attempted. When
   attempting it: `vscode.commands.executeCommand('buildTutorials.step.focus')` (VS Code
   auto-generates a `<viewId>.focus` command for every contributed view — no manual
   registration needed) BEFORE asserting anything that depends on `resolveWebviewView` having
   fired. If it does not fire in the vscode-test host within a reasonable await, fall back to
   asserting through `WalkSession`'s own state getter (a plain, non-test-suffixed `getView():
   WalkView` used by both `StepViewProvider` in production AND tests is fine — it is not
   `vscode`-shaped, so exposing it isn't a smell) rather than the rendered HTML, and SAY SO
   in the next handoff/report rather than silently downgrading the assertion.
8. **`package.json` additions needed (step 6, not yet made):** `viewsContainers.activitybar`:
   one entry `{ "id": "buildTutorials", "title": "Build Tutorials", "icon": "media/icon.svg" }`;
   `views.buildTutorials`: `buildTutorials.decisions` (tree, name "Decisions") and
   `buildTutorials.step` (type `webview`, name "Current Step"); commands
   `buildTutorials.openWalk`, `buildTutorials.nextStep`, `buildTutorials.prevStep`,
   `buildTutorials.goToStep` (the last needs an id argument — give it `menus.commandPalette`
   `"when": "false"` so it never shows up as a bare, argument-less palette entry);
   `menus.view/title` for next/prev, `"when": "view == buildTutorials.decisions"`, `"group":
   "navigation"`. No new `activationEvents` needed — VS Code >=1.74 infers view-activation
