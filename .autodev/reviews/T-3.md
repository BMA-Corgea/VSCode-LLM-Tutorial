**Reviewer:** fresh session, auto-review stage. **Branch:** `feature/T-3-start-screen` @

## Headline

This is careful, well-tested work: all 7 ACs are substantively implemented, the 87 tests
(74 unit + 13 vscode-test) really do pass, run twice, under both `DISPLAY=:1` and
`xvfb-run -a`, and several of the suite's more unusual claims — the AC6 fixture test running
through the actual rendered page, the fake-DOM suite really executing the shipped client
script, the skin-token census being derived from repo-tour's real `base.css` rather than a
hand-copied list — check out under independent re-derivation, not just re-reading. The
security-sensitive parts hold up under direct attack: an `<img src=x onerror=alert(1)>` idea
value and a `"><script>` breakout in the repo/target fields both come back fully escaped
through the real `renderStartHtml`, and the CSP is a strict `default-src 'none'` with
nonce-only style/script and no `unsafe-inline`.

That said, three real, independently-confirmed defects and one disclosed-but-real spec-text
miss keep this from a clean pass: (1) the resume-on-activate wiring in `extension.ts` never
clears its own `workspaceState` bookmark, so after the first build ever run in a workspace,
every future window activation loads the whole core and pops a progress notification for
nothing, forever — and this integration path has zero test coverage, unit or vscode-test; (2)
`plan.json`/`request.json` are written with a plain `writeFileSync`, not the temp-file+rename
pattern the write-ahead marker uses two functions away in the same file, so a crash mid-write
can leave a corrupt plan on disk; (3) the message handler does not validate the shape of
messages coming from the webview before acting on them — confirmed by directly feeding
`handleStartMessage` a non-string field and an unrecognized message type through the real
compiled code, both of which throw. None of these is a demonstrated exploit or a fundamentally
broken AC, which is why this is REWORK and not BLOCK — but they are concrete and worth fixing
before merge.

## Angle 2 — Security of the webview

- **CSP.** `src/webview/page.ts:70`: `default-src 'none'; style-src 'nonce-…'; script-src
  'nonce-…'` — one nonce per render (`randomBytes(16)`, confirmed fresh per call by
  `page.test.ts`'s "never reuses the previous nonce" test), every `<style>`/`<script>` tag
  carries it, no `unsafe-inline` anywhere in the diff (`grep -rn unsafe-inline src` — zero
  hits). repo-tour's `assets/skins/*.css` reference no `url()` resources at all, so the strict
  `default-src 'none'` costs nothing visually.
- **Escaping — verified against the real render function, not just its unit tests.** Bundled
  the actual `src/start/view.ts`/`src/start/request.ts`/`src/start/protocol.ts` with esbuild
  (no stub, no mock) and ran `renderStartHtml` with `idea = '<img src=x onerror=alert(1)>'` and
  `repo = target = '"><script>alert(2)</script>'`. Output:
  `<textarea id="idea" ...>&lt;img src=x onerror=alert(1)&gt;</textarea>`,
  `value="&quot;&gt;&lt;script&gt;alert(2)&lt;/script&gt;"` for both repo and target, and the
  same escaping in the `problem-idea` div. No raw `<img`/`<script>` anywhere in the output.
  Title, skin labels/notes (`pickerHtml`), and every problem message are escaped the same way
  (`src/webview/html.ts`'s `escapeHtml`/`escapeAttr`, used consistently everywhere user or
  repo-tour-provided text lands in markup).
- **Message-shape validation — a real, confirmed gap.** `handleStartMessage`
  (`src/start/protocol.ts:58-89`) and `StartPanel`'s listener
  (`this.panel.webview.onDidReceiveMessage((message: InboundMessage) => { void
  this.onMessage(message); }` — `src/start/panel.ts:64`) trust the incoming message's shape at
  compile time only; there is no runtime check. Fed the real compiled `handleStartMessage`
  directly:
  - `form:submit` with `{ repo: 12345, target: {evil:true} }` → throws
    `TypeError: repo.trim is not a function` (from `validateRepo`, `src/start/request.ts:68`).
  - an unrecognized `{ type: 'evil:message' }` → throws `unhandled start-screen message: ...`
    (the `default` branch, `src/start/protocol.ts:84-87`).
  - `payload: { request: null }` and a missing `payload` entirely → both throw
    (`Cannot read properties of null/undefined`).
  Any of these, dispatched through the real `onDidReceiveMessage` wiring, becomes an unhandled
  promise rejection rather than a graceful failure. **However**: `pick:repo`/`pick:target`
  carry no payload in the `InboundMessage` type at all and the chosen path always comes from
  `vscode.window.showOpenDialog`'s own result (`src/start/panel.ts:45-53`), never from message
  content — so the specific "pick:target with a crafted path" attack the review angle names is
  structurally impossible here regardless of this gap. Given the escaping above holds and the
  CSP is nonce-only with no external content, I found no actual path for a remote/webview-side
  attacker to *construct* an arbitrary postMessage in the first place; this is a real,
  confirmed defense-in-depth gap (and the review's own rubric names "an unvalidated message" as
  a gating category), not a demonstrated exploit.

## Angle 3 — The build pipeline (`src/start/build.ts`)

- **No `vscode` import** — confirmed by reading the whole file and by `grep -n vscode
  src/start/build.ts` (only doc-comment mentions). Every VS Code effect is threaded in via
  `BuildContext`/`ResumeContext`, wired only in `src/extension.ts`.
- **Marker lifecycle.** Written via temp-file + rename (`writeMarker`, lines 150-155) —
  genuinely atomic. `runPhase` (line 200) writes the marker *before* that phase's work runs;
  `test/unit/build.test.ts`'s "durably updated at each phase" test proves this by re-reading
  the marker from disk independently inside the `onPhase` hook, not from in-memory state.
  Deleted on success (line 279) and on an explicit cancel (`cancel()`, line 291-294, tested).
  **Deliberately left on a thrown failure** (digest/buildPlan/interpretPlan/write all throwing)
  — documented rationale (a transient failure might be worth retrying; digest/buildPlan are
  free to redo, interpretPlan is cache-keyed), tested directly
  ("a marker survives a THROWN digest error", line 361-373). This is a reasoned, disclosed
  design choice, not an oversight.
- **`cachedOnly` honoured** — threaded straight through to `interpretPlan`'s options
  (line 260).
- **GitHub clone.** Full clone, no `--depth` (`resolveRepo`, line 102, confirmed by
  `resolveRepo`'s test asserting `!args.includes('--depth')`), into
  `<globalStorageRoot>/refs/<owner>-<name>` (line 95), reused via `git fetch --all --tags` on a
  second call rather than re-cloning (line 96-98, tested).
- **Language refusal** — see Angle 1/AC3.
- **plan.json / request.json are NOT written atomically — gating.** `writeMarker` (same file,
  lines 150-155) explicitly uses a temp file + `fs.renameSync` specifically to avoid "a
  half-written marker" (its own comment). The actual deliverable, though
  (`buildFromRequest`, lines 272-274):
  ```
  fs.writeFileSync(path.join(buildDir(target), 'plan.json'), JSON.stringify(interpreted.plan, null, 2));
  fs.writeFileSync(path.join(buildDir(target), 'request.json'), JSON.stringify(request, null, 2));
  ```
  uses plain `writeFileSync`, no temp+rename. A crash exactly here leaves the marker behind
  (it's only deleted after these two writes succeed), so a *Resume* self-heals by re-writing
  the file in full — but a user who *Discards*, or simply never reloads within the 6-hour
  window, can be left with a truncated, invalid-JSON `plan.json` and no marker pointing at it,
  for T-4 (the walk) to trip over later with no explanation. No test exercises a crash between
  these two lines (understandably hard to simulate), so this is unexercised in either
  direction.

## Summary of findings

**Gating:**

1. **`resumeOnActivate` never clears its own bookmark; the resume-on-activate wiring is
   untested.** `src/extension.ts:103` sets `context.workspaceState`'s
   `buildTutorials.currentBuild` at the start of every build and it is never cleared anywhere
   (`grep -rn CURRENT_BUILD_KEY src/` shows only the one set + one read). `resumeOnActivate`
   (`src/extension.ts:137-155`) does not check whether a marker exists before committing to
   `loadCore(...)` and opening a `withProgress` "Build Tutorials" notification — it only checks
   this *inside* `resumeIfMarked`, after that cost is already paid. Net effect: after the first
   build ever completes in a workspace (success, refusal, or cancel — all leave the bookmark
   set), **every future window activation** reloads the whole repo-tour core and flashes an
   empty progress notification, forever, for no reason. No test — unit or vscode-test —
   exercises `resumeOnActivate` or this integration at all; only the lower-level,
   VS-Code-free `resumeIfMarked` is tested, which correctly returns fast but only after
   `extension.ts` has already paid the unnecessary cost. Confirmed by direct code reading and
   grep, not by spinning up a second real activation cycle (VS Code's `Extension.activate()` is
   idempotent within one process, and reproducing a genuine second startup without exporting
   internal functions I should not add would itself be a code change).
2. **`plan.json`/`request.json` are not written atomically**, unlike the marker two functions
   away in the same file. `src/start/build.ts:272-274` vs. the temp+rename pattern at
   `src/start/build.ts:150-155`. A crash mid-write can leave a corrupt `plan.json` that a
   *Discard* or a >6h-stale marker leaves behind with nothing to signal it's broken.
3. **The message handler does not validate incoming message shapes.** Confirmed by directly
   feeding the real, compiled `handleStartMessage` (`src/start/protocol.ts:58-89`) malformed
   payloads: a non-string `repo` field throws `TypeError: repo.trim is not a function`; an
   unrecognized `type` throws from the `default` branch; a null/missing `payload` throws.
   `src/start/panel.ts:64` calls this via `void this.onMessage(message)`, so any of the above
   becomes an unhandled promise rejection. Exploitability is unconfirmed and likely low — the
   escaping (Angle 2) is solid, the CSP is nonce-only with no `unsafe-inline`, and
   `pick:repo`/`pick:target` never trust webview-supplied paths in the first place — but the
   review's own rubric names "an unvalidated message" as a gating category, and this is a real,
   reproduced gap, not a theoretical one.

**Advisory:**

1. **AC2's honesty line is not byte-exact against this ticket's own spec text.**
   `.autodev/specs/T-3-start-screen.md:12` (the ticket's own AC2, "captured, not re-composed")
   reads `tick recreate to build from a repo` (no inner quotes, no trailing period). The
   implementation (`src/start/request.ts:53`) reads `tick 'recreate' to build from a repo`
   (inner quotes present) — matching the earlier `.autodev/specs/T-1-build-tutorials-v1.md:203-204`
   wording instead (which itself also has a trailing period the implementation lacks). The two
   spec documents disagree with each other, so this isn't cleanly the builder's fault, but the
   handoff's explicit "Verbatim" claim doesn't fully hold against the ticket's own text, and
   `test/unit/request.test.ts:42` hardcodes the same (quoted) string rather than deriving it
   from either spec file, so no existing test could have caught the drift. Trivial to reconcile
   either way; worth a PM decision on which source is canonical.
2. `page.ts`'s `restore()` helper is defined but never called in `src/start/view.ts` — `save()`
   only, write-only for this page (Angle 5). Not a functional gap; the host-authoritative
